# Roosevelt (Land-RAI)

Plataforma SaaS multi-tenant con SI (Roosevelt Super Intelligence). Modelo B2B **y B2C**: cada usuario, desde `/home`, crea perfiles empresariales (`type: 'empresa'`) y personales (`type: 'persona'`) y gestiona su vida personal y empresarial. UI, docs y commits en español. Repo: github.com/admluxorsys/land-rai.

- El producto se llama **Roosevelt Super Intelligence** (abreviado **SI**). **No** usar "AI", "IA" ni "Artificial Intelligence" en textos visibles (UI, metadatos, pie de página, legales). Next.js 16 (App Router, webpack en dev), React 18, TypeScript, Tailwind 3, Radix/shadcn, Framer Motion, Zustand, ReactFlow · API routes de Next + Cloud Functions mínimas (`functions/`, Node 20) · Firebase (Firestore, Auth, Storage) · SI (modelos): Gemini (+ SDKs Anthropic/OpenAI/Vertex) · Pagos: Stripe y Solana · Integraciones: WhatsApp Cloud API, Meta/Instagram, Gmail, Telegram, X, GitHub · Deploy: Vercel + Firebase (`roosevelt-491004`).

## Arquitectura
- **Tenancy:** todo dato de cliente vive bajo `users/{userId}/entities/{entityId}/...`. Regla de oro: nunca crear colecciones raíz con datos de cliente ni consultas `collectionGroup` sin filtro de tenant.
- **Seguridad (aislamiento entre clientes):**
  - `firestore.rules`: solo el dueño accede a `users/{uid}/**`; todo lo demás está denegado al SDK web (el servidor usa Admin SDK). Validado con el emulador (19 casos) y desplegado en producción el 2026-10-04 (reglas anteriores en `~/backups/`; revertir con `git show d1878be:firestore.rules`). Para probar reglas: JRE en `~/tools/` + `firebase emulators:exec --only firestore`. **Prohibido** agregar `/{document=**}` o `allow ...: if true`. Las consultas `collectionGroup` desde el navegador quedan denegadas: hacerlas en una ruta API (ejemplo: `api/integrations/check-unique`).
  - Rutas API (Admin SDK, ignoran las reglas): todo handler privado empieza con `const denied = await guardApi(req); if (denied) return denied;` (`src/lib/apiAuth.ts`). Verifica el ID token de Firebase y que `userId`/`u`/`uid` coincida con el token. El cliente adjunta el token solo (`installApiAuthFetch`, instalado en `AuthContext`). Modo por defecto `enforce`; interruptor de emergencia: `API_AUTH_MODE=log` (solo registra) en Vercel.
  - Rutas públicas por diseño (sin guard): webhooks (`whatsapp|meta|telegram|twitter|gmail/webhook`), `subscriptions/stripe-webhook`, callbacks OAuth (`gmail/callback`, `auth/github*`), `admin/migrate-mold` (secreto), `web-builder/cdn-proxy` (lista blanca de CDNs).
  - **Firma de webhooks (Fase 2, 2026-10-04)** `src/lib/webhookSignature.ts`: Meta/WhatsApp (`X-Hub-Signature-256` con `META_APP_SECRET`, admite varias apps en `META_APP_SECRETS`), X (`x-twitter-webhooks-signature` con `TWITTER_CONSUMER_SECRET`), Gmail (JWT OIDC de Pub/Sub; requiere `GMAIL_PUBSUB_AUDIENCE` y configurar autenticación en la suscripción push) y Telegram (`secret_token` por entidad en `integrations/telegram_internal`; los bots antiguos se permiten con aviso hasta reconectarlos). `WEBHOOK_SIGNATURE_MODE`: `log` (defecto, solo registra) o `enforce` (rechaza con 401). **Pasar a `enforce` en Vercel cuando los logs muestren `[webhook-sig] ... ok`.** Meta, WhatsApp, X y Gmail ignoran ids (página, número, cuenta, correo) reclamados por varios usuarios (anti-secuestro): no se entrega a nadie. **Reclamos verificados** (`src/lib/integrationClaims.ts`, colección raíz `integration_claims/{provider}__{id}` = solo `{userId, entityId}`, escrita únicamente por el servidor y denegada al navegador): tras conectar Messenger/Instagram/WhatsApp los modales llaman a `/api/integrations/claim`, que comprueba con Graph que el token controla el id; los webhooks resuelven primero por ese registro (un id escrito a mano en otra integración ya no desvía mensajes). Integraciones antiguas se reclaman solas por verificación diferida al recibir su primer mensaje. `INTEGRATION_CLAIMS_MODE`: `allow` (defecto, acepta ids sin reclamo con guarda de ambigüedad) o `require` (solo ids reclamados; activar cuando `integration_claims` ya tenga las conexiones existentes). Falta aplicar lo mismo a Gmail y X (X aún es maqueta).
  - Si creas una ruta nueva privada: agrega `guardApi`; si es un webhook: verifica firma/token del proveedor.
  - Respaldos: `~/backups/` (fuera del repo, contiene datos de clientes). Script de respaldo de solo lectura con Admin SDK; repetir antes de cambios riesgosos.
- **Integraciones: plataforma vs cliente (regla de oro).** Vercel guarda SOLO credenciales de las *apps de la plataforma* (Meta `NEXT_PUBLIC_META_APP_ID`/`META_APP_SECRET`, Google `GMAIL_CLIENT_*` + Pub/Sub, consumer key de X, GitHub OAuth, Stripe, Firebase Admin, Gemini). Todo lo del cliente (tokens de página/WhatsApp/IG, OAuth de Gmail y X, bot token de Telegram, `pageId`/`phoneNumberId`) vive en `users/{uid}/entities/{id}/integrations/*`. **Prohibido** leer tokens de cliente desde `process.env` (p. ej. `WHATSAPP_ACCESS_TOKEN`): un cliente sin credenciales enviaría con las del dueño. Los webhooks resuelven el tenant por el id del payload (`phone_number_id`, `pageId`, `instagramId`) con consultas filtradas; nunca `collectionGroup(...).get()` sin filtro ni "fallback" a otro tenant. `state` de OAuth firmado con `src/lib/oauthState.ts`. La página `/home/[entityId]/cto/integrations` es genérica (el molde es código; no hay "cuenta molde"): probar siempre con una cuenta de prueba aparte, no solo con la propia. Hoy la app de Meta está atada a un negocio propio: para que clientes ajenos conecten Facebook/Instagram/WhatsApp hace falta una app de plataforma en modo Live con App Review y verificación de empresa.
